## Qué aplicación se está reemplazando

El dashboard ya tiene un cliente Angular 15 integrado con la sesión y el adaptador de lectura v5. Emplea TypeScript, RxJS, PrimeNG para tablas y diálogos, Angular Material y localización por idioma. El menú distingue perfil, historial de cosechas, validaciones y estadísticas. El historial usa snapshots y representa cosechados, válidos y transformados. La pantalla de estadísticas carga un widget externo configurado por instalación y lo identifica con `stats_source_id`. Sus cifras tienen otra procedencia. [Dependencias](../lareferencia-repository-dashboard/angular/package.json) · [Rutas](../lareferencia-repository-dashboard/angular/src/app/app-routing.module.ts) · [Widget](../lareferencia-repository-dashboard/angular/src/app/statistics/pages/main.component.ts)

## Contrato de lectura que usa hoy

Las rutas de la tabla son GET relativos a `/api/v5/dashboard`. La sesión viaja por cookie. El cliente recupera la identidad con `/api/v5/me` y utiliza CSRF al iniciar y cerrar sesión. En la configuración de desarrollo Nginx limita los recursos de datos del host dashboard al adaptador. Spring comprueba el rol, la red o el snapshot y la coincidencia del acrónimo. El diseño admite ADMIN y DASHBOARD humano con redes asignadas. La matriz completa por host, red y rol sigue pendiente de prueba en navegador. [Sesión](../lareferencia-repository-dashboard/angular/src/app/core/services/authentication.service.ts) · [Gateway](../Docker/nginx/dev-dashboard-gateway.conf) · [Controlador](../lareferencia-lrharvester-app/src/main/java/org/lareferencia/backend/api/v5/ApiV5DashboardCompatibilityController.java)

| Pantalla o acción | Lectura y significado |
|---|---|
| Elegir fuente e histórico | `/harvesting/source/list` se recorre en páginas de 100. Para la fuente se consultan `/{acrónimo}`, `/{acrónimo}/lkg` o `/{acrónimo}/history` bajo `/harvesting/source`. El historial también admite intervalo y páginas. El controlador limita el historial a snapshots VALID. |
| Abrir informe | `/validation/source/{acrónimo}/{snapshot}` devuelve tamaño, válidos y reglas. El cliente normaliza `rulesByID` a lista y calcula inválidos por resta. Calcula conformidad por regla como aprobados / (aprobados + fallidos), con cero si el denominador es cero. |
| Filtrar registros | GET al mismo recurso con sufijo `/records`. Envía `pageNumber` desde cero, `pageSize`, `oai_identifier`, `is_valid`, `is_transformed`, `valid_rules` e `invalid_rules`. Las dos últimas admiten listas. La tabla lee `content` y `totalElements`. |
| Examinar una regla | «Details» abre dos tablas. `/valid_occrs/{regla}` e `/invalid_occrs/{regla}` devuelven pares valor/cantidad. Cada GET calcula ambos grupos en el backend y selecciona uno. Se descarga la lista del grupo completa y se pagina en el navegador. |
| Investigar fallos | La ruta Angular `/{acrónimo}/validation/{snapshot}/invalid_rule/{regla}` vuelve a leer resumen y fuente, resuelve el nombre y consulta `/records?invalid_rules=…`. La ruta simétrica de aprobados está comentada. La tabla general permite filtrar aprobados. |
| Abrir ficha | Combina la fila recibida con el catálogo de reglas para mostrar aprobaciones, fallos y valores por regla. El enlace OAI construye un GetRecord contra el proveedor de origen. Puede devolver metadatos actuales, distintos de los que evaluó el snapshot. |

Fuentes del recorrido: [servicio de cosechas](../lareferencia-repository-dashboard/angular/src/app/core/services/harvesting.service.ts), [servicio de validación](../lareferencia-repository-dashboard/angular/src/app/core/services/validation.service.ts), [rutas de validación](../lareferencia-repository-dashboard/angular/src/app/validations/validations-routing.module.ts) y [tabla de registros](../lareferencia-repository-dashboard/angular/src/app/validations/components/records/records-table/records-table.component.html). El adaptador expone además `/validation/source/stats/{acrónimo}/{snapshot}/query`; el servicio Angular de validación no lo invoca.

## Decisiones y verificación siguiente

1. Conservar como recorridos de referencia el histórico por fuente, la comparación entre reglas, el acceso directo a los registros que fallan una regla y la ficha con valores. Usar la API compartida de estadísticas para que el admin y el dashboard lean los mismos resultados. Los permisos del dashboard deben seguir aplicándose en el servidor.
2. Decidir si al filtrar registros el resumen y las frecuencias deben seguir la selección o permanecer globales con una etiqueta explícita. Acordar asimismo qué exportaciones abarcan todos los resultados. Estas decisiones afectan tanto al contrato como al coste de consulta.
3. Resolver por separado el acceso al XML publicado del snapshot y a los logs. El recorrido observado ofrece el enlace OAI externo; incorporar XML histórico o bitácora requiere una decisión de acceso por red y una ruta admitida por el gateway.
4. Reproducir en Chrome por el host dashboard con una copia de Docker. Usar AREANDINA #6, un histórico incompleto, una fuente sin snapshot válido y una cuenta DASHBOARD de una sola red. Guardar respuestas y captura del informe al filtrar, abrir una regla, consultar la ficha y exportar. Verificar también acceso ajeno y sesión vencida. Los hallazgos anteriores proceden de inspección de código; la prueba previa de Chrome corresponde al admin.

**Comprobación técnica.** Se copiaron el código Angular, los manifiestos npm y los tsconfig a un directorio temporal. Con Node 18, `npm ci --legacy-peer-deps` y `tsc -p tsconfig.app.json --noEmit` terminaron correctamente. Esto comprueba tipos TypeScript. El renderizado de plantillas, las sesiones y las llamadas HTTP requieren el recorrido funcional descrito arriba.
