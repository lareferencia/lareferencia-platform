## Propuesta y alcance

Construir una aplicación React autónoma en `lareferencia-repository-dashboard/web/`. Tomar del admin una copia identificada de componentes, estilos y pruebas. El dashboard tendrá su propio `package.json`, lock npm, cliente HTTP, traducciones, rutas, pruebas y bundle. Debe poder compilar con un checkout del dashboard y Node, sin instalar ni importar el admin. El reactor Maven seguirá siendo la vía de empaquetado para la plataforma. Mantener Angular en el mismo repositorio como referencia funcional hasta la aceptación y el cambio de artefacto.

Referencias iniciales publicadas: plataforma `693385a`, admin-web `5dacfdb`, harvester `d919a07`, core `0c52e97`, dashboard Angular `1d429d7`. Al copiar, conservar avisos de licencia y registrar el archivo y commit de origen en el primer cambio de dashboard. En adelante cada repo será dueño de su copia. Una corrección de sesión, accesibilidad o diagnóstico que afecte a ambos requiere portar el cambio y su regresión al otro repo. ## La dependencia que condiciona la migración

El admin consulta resumen, registros y frecuencias mediante POST a la API nativa de snapshots. El host dashboard de desarrollo admite GET bajo `/api/v5/dashboard/**` y tiene excepciones concretas para sesión. La pantalla React copiada fallaría si conserva los métodos HTTP del admin. Ampliar permisos al rol DASHBOARD para consumir el cliente administrativo completo tampoco forma parte de esta propuesta. [Gateway actual](../Docker/nginx/dev-dashboard-gateway.conf) · [Controlador de lectura](../lareferencia-lrharvester-app/src/main/java/org/lareferencia/backend/api/v5/ApiV5DashboardCompatibilityController.java)

**Primera entrega viable con el contrato existente.** Implementar un cliente tipado de dashboard que lea fuentes, historial, último válido, resumen, registros y ambos grupos de ocurrencias por las rutas GET actuales. Mapear DTOs por nombre y significado: por ejemplo, `content/totalElements`, `rulesByID`, `ruleID`, obligatoriedad nullable y mapas de valores por registro. Verificar las respuestas reales antes de dar tipos por compatibles. La llave de cada consulta incluirá red, snapshot, filtros y página según corresponda. Mantener visibles los totales globales del snapshot y el total de registros seleccionados con rótulos explícitos. Esta entrega permite probar la aplicación completa con el gateway actual.

**Mejora propuesta para aprobar antes de tocar el backend.** Si queremos que, como en el admin, el resumen y las frecuencias sigan todos los filtros, el contrato actual solo permite aplicarlos a la tabla. Proponer parámetros de consulta opcionales en el GET de resumen y una lectura conjunta de frecuencias válidas e inválidas con los mismos filtros. Delegar en las consultas de estadísticas ya corregidas en core, conservar las respuestas existentes sin parámetros y comprobar rol, asignación y coherencia acrónimo/snapshot en cada lectura. Medir el tamaño de URL de las multiselecciones antes de elegir GET o un POST de consulta específico. Esta segunda opción también requiere acordar la ruta, CSRF y la regla correspondiente en el gateway. El dato para decidir es la experiencia deseada, no el framework.

**Dos decisiones independientes.** El GetRecord del proveedor ya es parte del dashboard y debe mantenerse. Entregar el XML publicado de un snapshot y exponer bitácoras son prestaciones adicionales con permisos por red por definir. Mantener esas opciones fuera de la interfaz hasta tener contrato aprobado. En CSV, la propuesta inicial es etiquetar explícitamente «página actual» en registros e historial y «reglas visibles» en la tabla de reglas; una descarga de todo el resultado requeriría diseño y medición específicos.

## Pruebas de aceptación prioritarias

- **Cifras.** AREANDINA #6 tiene 4.000 registros activos. La regla 5 tiene 1.871 aprobaciones y 2.129 fallos. En regla 10 hay 9.971 ocurrencias globales y 7.623 dentro de los que aprueban la regla 5. Comparar IDs, filas, denominadores y total paginado. Comprobar que una edición posterior del validador conserva cifras y reglas históricas. Mostrar «sin evaluaciones» cuando el denominador sea cero.
- **Errores y navegación.** Una regla inexistente o un snapshot ajeno deben producir un estado comprensible. Inducir un 503 solo en registros, reintentar conservando filtros, y retrasar dos respuestas en orden inverso. Validar que la última selección permanece en pantalla. Verificar que un vacío de frecuencias distingue captura desactivada o desconocida cuando los datos lo permiten.
- **Archivos y enlaces.** Leer el CSV generado y comparar cabeceras, columnas, filas, comillas y caracteres acentuados. Confirmar que coincide con el alcance anunciado. Comprobar la ruta de fallos por regla y que el enlace OAI conserva el identificador completo.
- **Acceso real.** Probar por Nginx ADMIN, DASHBOARD con red asignada y ajena, DASHBOARD sin asignaciones, READER, cuenta técnica y sesión expirada. Registrar respuesta del host y del backend cuando proceda. Comprobar el aislamiento también pegando una URL y alternando usuarios.
- **Operación.** Datos históricos, fechas límite, varios idiomas, teclado y vista móvil. Medir solicitudes y p50/p95 de resumen, registros y frecuencias en dos tamaños de snapshot, caché fría y caliente, comparados con la referencia de fase 0. Fijar el umbral con esas medidas.

## Esfuerzo y primera decisión

Estimación preliminar para una persona familiarizada con ambos frontends, con revisión funcional disponible: 2–3 jornadas para referencia y contrato, 2–4 para base/sesión, 5–8 para diagnóstico y exportaciones, 4–7 para historial, gráficas, perfil y widget, y 3–5 para integración y aceptación. **Total orientativo: 16–27 jornadas**. Depende de disponer de una configuración representativa del widget, copias de datos y acceso al gateway de prueba. Estimar por separado las ampliaciones de API y descargas masivas después de acordar su alcance.

La primera inversión sería una sección vertical que arranque en login, pase por el selector de fuente y termine en una regla de AREANDINA #6, servida por el host dashboard. Con ella se validan de una vez la copia visual, la independencia del nuevo proyecto, los permisos y la adaptación de datos. Esa evidencia permite ajustar el esfuerzo restante antes de comprometer el corte.
